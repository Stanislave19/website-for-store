# Магазин годинників

Інтернет-магазин наручних годинників. Модель — дропшипінг (складу немає, товар замовляється під замовлення; для клієнта завжди «в наявності»).

Зараз працюємо над **MVP** (каталог + заявки, без онлайн-оплати).

Активні документи MVP (тримати в контексті):
- @docs/specyfikaciya-mvp.md — що система вміє
- @docs/database-schema-mvp.md — схема бази (15 таблиць)
- @docs/api-endpoints-mvp.md — REST API
- @docs/design-system.md — візуальні правила (палітра Racing Green & Brass, Fraunces + Work Sans)

Дизайн сторінок (читати, коли верстаєш відповідний екран):
`docs/page-home.md` · `docs/page-catalog.md` · `docs/page-product.md` · `docs/page-cart.md` · `docs/page-checkout.md`
Скріншоти макетів — у `docs/design/` (home-1..4, catalog-1..3, product-1..4, cart-1..3, checkout-1..3). Скріншот показує, ЯК має виглядати; точні значення — у page-документі; джерело правди для палітри — design-system.md.

`docs/specyfikaciya-prod.md`, `docs/database-schema-prod.md`, `docs/api-endpoints-prod.md`. Прод-документи будуються поверх MVP і описують лише різницю (оплата, повернення, статуси).

## Стек

- Backend: FastAPI + PostgreSQL (SQLAlchemy, Alembic, Pydantic)
- Frontend: Next.js + Tailwind CSS
- Архітектура: два окремі проєкти (`backend/`, `frontend/`), спілкування через REST API
- Docker: кожен сервіс контейнеризовано; `docker-compose.yml` піднімає все разом (backend, frontend, PostgreSQL, Nginx)

## Команди

- Усе разом (backend + frontend + PostgreSQL + nginx): `docker-compose up` (з кореня проєкту)
- Backend dev (без Docker, з `backend/`): `uvicorn app.main:app --reload`
- Backend тести (з `backend/`): TODO — з'явиться разом із першими тестами

## Правила

- Мова інтерфейсу та контенту — тільки українська. Валюта — тільки гривня.
- Атрибути товару (бренд, матеріал тощо) зберігати як окремі таблиці-довідники зі зв'язками, НЕ як текстові поля. Це захищає від дублів і потрібне для фільтрів.
- Телефон клієнта — обов'язковий, з валідацією формату +380.
- Клієнтська й адмінська зони розділені, окремий захищений вхід в адмінку.
- SEO критичний: сторінки товарів і каталогу — через серверний рендеринг Next.js, з мета-тегами й картою сайту.
- Адаптивність mobile-first: більшість покупців з телефону.
- Товарів 1000+: передбачити масовий імпорт через Excel/CSV, а не лише ручне додавання.
- Проєкт від початку структурувати під Docker (Dockerfile для backend і frontend, спільний docker-compose.yml) — сервер ще не обрано, тож рішення має лишатися незалежним від провайдера.
- Дотримуватися розмежування MVP / прод: не додавати логіку оплати, поки працюємо над MVP.

## Робочий процес

- Складні або багатофайлові зміни — спершу показати план, тоді виконувати.
- Не робити масштабних змін поза поточним завданням без узгодження.

## Git і звітність (важливо)

Я не пишу код сам — я контролюю роботу й реагую на помилки. Тому:

- **Репозиторій**: https://github.com/Stanislave19/website-for-store
- **Авторство комітів — тільки моє.** НЕ додавати в повідомлення коміта жодних згадок Claude, Claude Code, AI, co-authored-by, generated with тощо. Коміти мають виглядати як написані мною. Використовувати мої git-налаштування (user.name / user.email), не змінювати їх.
- **Комітити часто**: після кожного завершеного логічного кроку, а не раз на етап. Дрібні коміти = точні точки відкату, якщо щось зламається.
- **Осмислені повідомлення комітів** українською або англійською, але зрозумілі: що саме змінилось і навіщо (не «fix», не «update»).
- **Пушити на GitHub** регулярно, щоб історія була доступна віддалено.
- **Після кожного кроку пояснювати простою мовою**, що зроблено: які файли створено/змінено, що тепер працює, що можна перевірити. Без жаргону — я не читаю код, я перевіряю результат.
- **Завжди казати, ЯК це запустити й перевірити вручну.** Конкретно: яку команду виконати (дослівно, щоб скопіювати), яку адресу відкрити в браузері, що саме я маю там побачити, якщо все правильно. Не «перевір, що API працює», а «виконай `docker-compose up`, відкрий http://localhost:8000/docs — маєш побачити список ендпоінтів».
- Якщо перевірка потребує тестових даних — сказати, звідки їх узяти або створити їх.
- Якщо щось не запуститься — одразу пояснити, які типові помилки бувають і як їх читати.
- Якщо крок великий — розбити на під-кроки з окремими комітами.
- Перед ризикованими змінами (міграції, зміна схеми, рефактор) — коміт до, щоб було куди відкотитись.
