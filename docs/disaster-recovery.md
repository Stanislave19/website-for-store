# Відновлення сервера з нуля

> Сценарій: VPS повністю втрачено (злетів диск, провайдер видалив інстанс, будь-що). Є лише: код на GitHub, останні бекапи (локально на старому сервері їх уже нема — беремо з офсайт-копії, див. `scripts/backup-db.sh`), і секрети, які мають зберігатись окремо від сервера (менеджер паролів, нотатки — НЕ git, `.env` туди ніколи не потрапляв).

## Що потрібно мати під рукою заздалегідь (не під час аварії)

Секрети з `.env` ніде, крім самого сервера, не зберігаються (і не повинні — у git їх немає). Тому **до** будь-якої аварії варто мати їх копію в менеджері паролів:
- `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`
- `SECRET_KEY`
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_IDS`
- `NOVA_POSHTA_API_KEY`
- дані доступу до офсайт-сховища бекапів (Backblaze B2 — ключ і бакет, див. `scripts/backup-db.sh`)
- домен і де керується DNS (щоб знати, куди йти оновлювати A-запис)

Якщо цієї копії немає — знайти ці значення більше ніде не вийде (крім Telegram-токена, який можна перевипустити через @BotFather, і Нової Пошти — перевипустити ключ у кабінеті).

## Кроки відновлення

### 1. Новий сервер
Підняти новий VPS (Ubuntu 22.04/24.04 — або будь-який дистрибутив, де є Docker). Встановити Docker і Docker Compose plugin:
```bash
curl -fsSL https://get.docker.com | sh
```

### 2. Код
```bash
git clone https://github.com/Stanislave19/website-for-store.git
cd website-for-store
```

### 3. Відновити `.env`
Скопіювати `.env.example` в `.env` і заповнити реальними значеннями з менеджера паролів (не з git — там їх немає):
```bash
cp .env.example .env
nano .env
```
Звернути увагу: `SECRET_KEY` — той самий, що був на старому сервері (інакше всі видані токени адмінки/клієнтів стануть недійсними, це не критично, просто всі перелогиняться, але краще відновити той самий). `NEXT_PUBLIC_SITE_URL` — актуальний домен.

### 4. Дістати останні бекапи з офсайт-сховища
Локальні бекапи (`backups/`) на мертвому сервері недоступні — беремо копію, яку `scripts/backup-db.sh` вивантажує в Backblaze B2 (`rclone`). На новому сервері:
```bash
# встановити rclone і підняти той самий конфіг (ключ доступу до B2 — з менеджера паролів)
curl https://rclone.org/install.sh | sudo bash
rclone config   # створити remote "b2backup" (тип b2), дані — з менеджера паролів

mkdir -p backups
rclone copy b2backup:lerom-backups/ backups/ --include "*-$(rclone lsf b2backup:lerom-backups/ | grep backup- | sort | tail -1 | grep -oE '[0-9]{8}-[0-9]{6}')*"
# або простіше — скопіювати все й вибрати найсвіжіше вручну:
rclone copy b2backup:lerom-backups/ backups/
ls -la backups/   # знайти найновіші backup-*.sql і media-*.tar.gz за міткою часу в назві
```

### 5. Підняти базу й backend (поки без відновлення даних)
```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d db backend
```
Зачекати кілька секунд, поки postgres підніметься (`docker compose logs db`).

### 6. Відновити базу даних
```bash
docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" < backups/backup-НАЙНОВІШИЙ.sql
```
(`$POSTGRES_USER` підтягнеться з `.env`, якщо виконувати з кореня проєкту через `set -a; source .env; set +a` перед командою — або підставити значення вручну.)

Якщо в коді з часу останнього бекапу з'явились нові Alembic-міграції (перевірити `backend/alembic/versions/` на GitHub на дату новіші за бекап) — прогнати їх:
```bash
docker compose exec backend alembic upgrade head
```

### 7. Відновити фото товарів
```bash
docker compose exec -T backend tar xzf - -C /app/media < backups/media-НАЙНОВІШИЙ.tar.gz
```

### 8. Підняти решту стеку
```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```
Усі 4 контейнери (`db`, `backend`, `frontend`, `nginx`) мають піднятись.

### 9. HTTPS-сертифікат
Сертифікат Let's Encrypt на старому сервері не переноситься (прив'язаний до файлової системи). Випустити новий за `docs/https-setup.md` (кроки 2-4) — займає кілька хвилин, доменом уже володієте.

### 10. DNS
Якщо IP нового сервера відрізняється від старого — оновити A-запис домену на нову адресу. Поширення DNS може зайняти до кількох годин.

### 11. Перевірка
- Сайт відкривається на домені (`https://ваш-домен`), каталог показує товари, ціни коректні.
- Фото товарів завантажуються (перевірити кілька карток) — підтверджує, що `media_data` відновився.
- Тестове замовлення проходить, Telegram-сповіщення приходить менеджеру.
- Вхід в адмінку працює зі старими обліковими даними (вони в базі, яку щойно відновили).

## Що НЕ відновлюється автоматично

- Дані між останнім бекапом (щоночі о 3:00) і моментом аварії — втрачаються. Замовлення чи зміни в товарах за цей проміжок доведеться вносити вручну, якщо є де їх узяти (Telegram-історія сповіщень про замовлення — фактична підстраховка на цей випадок).
- HTTPS-сертифікат — випускається заново (крок 9), не відновлюється з бекапу.

Цей документ варто раз на кілька місяців перевіряти на практиці (підняти новий сервер із бекапу в тестовому режимі) — інструкція, яку жодного разу не виконували, часто виявляється неповною саме в момент, коли вона дійсно потрібна.
