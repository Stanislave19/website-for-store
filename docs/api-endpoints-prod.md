# API-ендпоінти — Прод (повна версія)

> REST API для продакшн-версії. Будується поверх MVP: усі ендпоінти MVP лишаються без змін, ДОДАЄТЬСЯ блок оплати LiqPay і кілька змін у логіці замовлень.
> Цей документ описує ТІЛЬКИ те, що додається або змінюється порівняно з `api-endpoints-mvp.md` (MVP). Усе, що там є і тут не згадано, лишається як у MVP.

## Позначення

- 🔓 публічний, 🔒 адмін (manager / owner)
- Базовий префікс `/api`, формат JSON

---

## Що лишається без змін (з MVP)

Каталог, фільтри, картка товару, категорії, кошик/промокод, wishlist, акаунт клієнта, налаштування вітрини, уся адмінка (товари, категорії, довідники, промокоди, налаштування) — **без змін**. Дивись `api-endpoints-mvp.md`.

## ЩО ЗМІНЮЄТЬСЯ

### Оформлення замовлення — додається вибір оплати

**🔓 POST `/api/orders`** — створити замовлення (розширюється)
Додаються поля в тіло:
- `payment_method` — `online` (повна оплата) або `cod_prepay` (наложка з передоплатою 150 грн)
Логіка змінюється:
- Якщо `cod` без передоплати — як у MVP (статус `new`, менеджер дзвонить).
- Якщо `online` або `cod_prepay` — замовлення створюється зі статусом `awaiting_payment`, у відповіді повертається посилання/дані для переходу на оплату LiqPay (див. нижче). Telegram менеджеру шлеться ПІСЛЯ підтвердження оплати, а не одразу.

### Статуси замовлення — розширюються

До MVP-статусів (`new` → `processing` → `confirmed` → `shipped` → `completed`, `cancelled`) додаються:
- `awaiting_payment` — створено, чекає оплати онлайн
- `awaiting_confirmation` — оплата пройшла, чекає перевірки наявності в постачальника (ключовий статус дропшипінгу)
- `refunded` — кошти повернено (товару не було)

---

## ДОДАЄТЬСЯ: Оплата (LiqPay)

**🔓 POST `/api/payments/create`** — ініціювати оплату для замовлення
Тіло: `{ order_id }`
Дії: рахує суму (повна ціна або 150 грн передоплати), формує дані для LiqPay (з підписом на боці сервера), повертає їх фронту.
Повертає: дані/посилання для віджета LiqPay, куди клієнт вводить картку (на боці LiqPay, не на сайті).

**🔓 POST `/api/payments/liqpay/callback`** — вебхук від LiqPay
> Це НЕ клієнтський ендпоінт — його викликає сервер LiqPay після оплати.
Дії бекенду (критично для безпеки):
1. **Перевірити підпис** запиту секретним ключем — якщо не збігається, відхилити (захист від фальшивих «оплат»).
2. Якщо оплата успішна — перевести замовлення в `awaiting_confirmation`, надіслати Telegram менеджеру.
3. Якщо помилка/відмова — лишити `awaiting_payment` або позначити відповідно.
Повертає: 200 для LiqPay (підтвердження отримання).

**🔓 GET `/api/payments/status/{order_id}`** — статус оплати замовлення
Для фронту: після повернення з LiqPay клієнт бачить, чи оплата пройшла (сторінка «дякуємо / оплату отримано» чи «очікуємо оплату»).

---

## ДОДАЄТЬСЯ: Адмінка — оплата й повернення

**🔒 PATCH `/api/admin/orders/{id}`** — розширюється
Менеджер може перевести замовлення з `awaiting_confirmation` у:
- `confirmed` (товар є в постачальника — виконуємо)
- `cancelled` + ініціювати повернення коштів (товару немає)

**🔒 POST `/api/admin/orders/{id}/refund`** — повернути кошти через LiqPay
Дії: викликає refund LiqPay для цього замовлення, переводить статус у `refunded`.
Тільки для замовлень, де оплата реально пройшла.

---

## ДОДАЄТЬСЯ: поля у відповідях

У деталях замовлення (`/api/admin/orders/{id}` і `/api/account/orders`) додаються:
- `payment_method` — online / cod_prepay / cod
- `payment_status` — не оплачено / оплачено / повернено
- `paid_amount` — скільки реально сплачено (повна сума або 150 грн передоплати)

---

## Що потрібно на сервері для проду (нагадування)

- Ключі LiqPay (public + private) — у захищених змінних оточення, НЕ в коді.
- Вебхук `/api/payments/liqpay/callback` доступний ззовні по HTTPS (LiqPay має до нього достукатись).
- Сторінка умов передоплати (неповернення при відмові) + згода при оформленні для `cod_prepay`.

---

## Загальні технічні правила (доповнення до MVP)

- Дані карток НЕ проходять через сервер — тільки через LiqPay.
- Підпис вебхука перевіряється ЗАВЖДИ, перш ніж змінити статус замовлення.
- Ідемпотентність вебхука: якщо LiqPay надішле callback двічі, замовлення не має оплатитись/змінитись двічі.
- Сума оплати рахується на сервері, НЕ приймається від клієнта (захист від підміни ціни).
