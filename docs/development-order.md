# Порядок розробки — MVP

> Покроковий план для роботи з Claude Code. Кожен крок — окремий етап: спершу зробити, перевірити, що працює, і лише тоді рухатись далі. НЕ намагатися зробити все одразу. Кожен крок будується на попередньому.

## Принцип

Будуємо знизу вгору: спочатку фундамент (база), потім бекенд (щоб віддавав дані), потім фронтенд (щоб показував), в кінці адмінку. Каталог — раніше за замовлення. Так на кожному етапі є щось працююче, що можна перевірити.

Порада для роботи: давай Claude Code один крок за раз. Після кожного — переконайся, що працює (запусти, перевір), і тільки тоді переходь до наступного. Якщо крок великий — розбивай на під-кроки.

## Етап 0. Каркас проєкту

Мета: порожній, але робочий скелет.
- Ініціалізація Git-репозиторію + підключення до GitHub (перший коміт — структура)
- Структура папок (backend / frontend / docs / nginx) за `project-structure.md`
- Docker: Dockerfile для backend і frontend, docker-compose.yml (backend + frontend + PostgreSQL + nginx)
- `.env.example`, `.gitignore` (обов'язково виключити .env, media/, node_modules, __pycache__)
- Заповнити розділ «Команди» в CLAUDE.md реальними командами (замість TODO)
- Перевірка: `docker-compose up` піднімає всі контейнери без помилок; порожній FastAPI відповідає на `/`, порожній Next.js відкривається в браузері; код запушено на GitHub.

## Етап 1. База даних

Мета: усі таблиці існують.
- SQLAlchemy-моделі за `database-schema-mvp.md` (усі 15 таблиць, розбиті по файлах: catalog, attributes, orders, users, shop)
- Alembic: перша міграція, що створює всю схему
- Enum-и (статуси, ролі, способи доставки, стать) в constants
- Перевірка: міграція застосовується, таблиці з'являються в PostgreSQL, зв'язки коректні.

---

## Етап 2. Довідники й каталог — бекенд (читання)

Мета: API віддає товари й фільтри.
- Схеми (Pydantic) для товару, категорії, фільтрів
- Сервіс каталогу: вибірка з фільтрами, пошуком, сортуванням, пагінацією
- Публічні ендпоінти: `GET /api/products`, `GET /api/products/{slug}`, `GET /api/categories`, `GET /api/filters`
- Перевірка: через Swagger (`/docs`) видно товари; фільтри й пошук працюють (спершу на кількох тестових товарах, доданих вручну).

---

## Етап 3. Каталог — фронтенд

Мета: клієнт бачить товари.

> **Дизайн:** усі екрани мають готові макети. Спершу прочитати `design-system.md` (палітра Racing Green & Brass, Fraunces + Work Sans, компоненти), потім `page-*.md` для конкретної сторінки й відповідні скріншоти в `docs/design/`. Скріншот показує, ЯК має виглядати; page-документ дає точні значення; design-system — джерело правди для кольорів і шрифтів.

- Налаштувати Tailwind (кольори й шрифти з `design-system.md`), підключити Google Fonts (Fraunces, Work Sans) і `lucide-react`
- Спільний каркас (layout): шапка з навігацією (Каталог · Про нас · Гарантія · Контакти) + іконки (пошук, wishlist, кошик, користувач), футер — за `page-catalog.md`
- Головна сторінка — за `page-home.md` + `design/home-1..5.png`
- Каталог — за `page-catalog.md` + `design/catalog-1..3.png`: фільтри-теги (не чекбокси!), повзунок ціни, сортування, пагінація
- Картка товару (`product/[slug]`) — за `page-product.md` + `design/product-1..4.png`
- Статичні сторінки: Про нас, Гарантія, Контакти
- `lib/api.ts` — звернення до бекенду
- Перевірка: у браузері видно каталог, фільтри звужують список, картка відкривається, статичні сторінки працюють, серверний рендеринг працює (перегляд коду сторінки показує контент).

## Етап 4. Кошик і список бажань

Мета: клієнт збирає замовлення.
- Кошик (у браузері, `useCart` на localStorage): додавання, видалення, кількість, сума — за `page-cart.md` + `design/cart-1..3.png` (включно з порожнім станом)
- Wishlist гостя (localStorage, `useWishlist`) — сітка як у каталозі
- Перевірка промокоду: `POST /api/cart/validate-promo` + поле вводу на фронті
- Перевірка: товар додається в кошик, кількість міняється, сума рахується, промокод застосовується, порожній стан показується.

---

## Етап 5. Оформлення заявки

Мета: замовлення доходить до менеджера.
- Форма checkout — за `page-checkout.md` + `design/checkout-1..3.png`: ім'я, прізвище, телефон (+380, валідація), місто, спосіб доставки (картки 2×2), відділення НП, спосіб зв'язку, коментар
- Бекенд: `POST /api/orders` — валідація, підрахунок суми, збереження зі статусом `new`
- Telegram-сервіс: сповіщення менеджеру (номер заявки, список моделей із цінами, сума, контакти, доставка, спосіб зв'язку, коментар)
- Екран-підтвердження (order-success) з номером заявки
- Перевірка: заявка створюється, зберігається в базі, менеджер отримує Telegram, клієнт бачить підтвердження.

---

## Етап 6. Адмінка — вхід і товари

Мета: менеджер керує товарами.
- Автентифікація персоналу: `POST /api/admin/login`, JWT, розділення від клієнтського входу
- Захист адмін-ендпоінтів (перевірка ролі manager/owner)
- CRUD товарів: список, створення, редагування, видалення, фото
- Форма товару з випадаючими списками з довідників
- Адмін-сторінки на фронті (окрема зона `/admin`)
- Перевірка: менеджер входить, додає/редагує товар, він з'являється в каталозі.

---

## Етап 7. Адмінка — довідники, категорії, замовлення, промокоди

Мета: повне керування.
- CRUD категорій (з підкатегоріями)
- CRUD довідників (бренди, механізми, типи й значення атрибутів)
- Перегляд замовлень, зміна статусів
- CRUD промокодів
- Налаштування (соцмережі, месенджери) — owner
- Перевірка: усі розділи адмінки працюють, зміни відображаються на вітрині.

---

## Етап 8. Масовий імпорт товарів

Мета: завести 1000+ товарів.
- `POST /api/admin/products/import` — читання Excel/CSV
- Upsert-логіка довідників (знайти або створити бренд/механізм/атрибути без дублів)
- Звіт про імпорт (додано / помилки)
- Визначити й задокументувати формат CSV (колонки) — стик із парсером
- Перевірка: тестовий файл на кілька десятків товарів імпортується коректно, дублі довідників не створюються.

---

## Етап 9. Акаунт клієнта (опційно)

Мета: зручність для повторних покупців.
- Реєстрація / вхід клієнта
- Історія замовлень, збережені адреси, серверний wishlist
- Перевірка: клієнт реєструється, бачить історію, зберігає адресу.

---

## Етап 10. Поліш, SEO, безпека

Мета: готовність до запуску.
- **SEO:**
  - Мета-теги (унікальні title/description на кожну сторінку)
  - Карта сайту (sitemap.xml) + robots.txt
  - **Structured data (JSON-LD)** на картці товару: schema.org Product + Offer (ціна, наявність, бренд, фото)
  - **Canonical / noindex для фільтрів** — комбінації 14 фільтрів дають тисячі URL-дублів; сторінки з query-фільтрами не індексувати
  - Оптимізація зображень, швидкість
- Адаптивність: перевірка на мобільному
- **Утиліта відмінювання числівників** (`pluralize`) — «571 модель», не «571 моделей»
- Безпека: HTTPS (сертифікат у nginx), захист від типових атак, 2FA власника
- Резервні копії бази
- Соцмережі й кнопки месенджерів (Telegram, Viber) у футері
- Перевірка: сайт коректний на телефоні, індексується, захищений, лічильники граматично правильні.

## Після MVP → Прод (чек-лист переходу)

Коли MVP працює й ФОП відкрито. Виконувати по порядку:

**1. Підготовка (поза кодом)**
- [ ] Відкрито ФОП або ТОВ
- [ ] Є банківський рахунок
- [ ] Зареєстровано в LiqPay, отримано ключі (public + private)
- [ ] Ключі покладено в захищені змінні оточення (`.env`), НЕ в код і НЕ в git

**2. Перемкнути CLAUDE.md на прод**
- [ ] Змінити рядок «Зараз працюємо над **MVP**» → «Зараз працюємо над **продом**»
- [ ] Переключити `@`-посилання: замість `specyfikaciya-mvp.md` / `database-schema-mvp.md` / `api-endpoints-mvp.md` підключити відповідні `*-prod.md`
- [ ] MVP-документи лишити як довідники (без `@`), бо прод описує лише різницю поверх них
- [ ] **Прибрати правило** «не додавати логіку оплати, поки працюємо над MVP» — воно більше не діє
- [ ] Додати правило: ключі LiqPay тільки в env; підпис вебхука перевіряти завжди

**3. База даних**
- [ ] Міграція: додати в `orders` поля `payment_method`, `payment_status`, `paid_amount`
- [ ] Міграція: розширити enum статусів (`awaiting_payment`, `awaiting_confirmation`, `refunded`)
- [ ] Міграція: створити таблицю `payment_transactions`
- [ ] Коміт ДО міграції (щоб було куди відкотитись)

**4. Код**
- [ ] `models/payments.py`, `services/payment_service.py`, `api/public/payments.py` — нові файли, наявне НЕ переробляти
- [ ] Ендпоінти: `POST /api/payments/create`, `POST /api/payments/liqpay/callback` (з перевіркою підпису!), `GET /api/payments/status/{order_id}`
- [ ] Адмінка: `POST /api/admin/orders/{id}/refund`
- [ ] Форма checkout: додати вибір способу оплати (онлайн / наложка з передоплатою)
- [ ] Telegram менеджеру: додати спосіб і статус оплати; для онлайн-оплати слати ПІСЛЯ підтвердження

**5. Перевірка**
- [ ] Тестова оплата проходить, вебхук приймається, підпис перевіряється
- [ ] Фальшивий вебхук (без правильного підпису) відхиляється
- [ ] Повторний вебхук не оплачує замовлення двічі (ідемпотентність)
- [ ] Сума рахується на сервері, не приймається від клієнта
- [ ] Повернення коштів працює
- [ ] Замовлення проходить статус «очікує підтвердження» перед виконанням

**Головне:** наявний код каталогу, кошика й замовлень НЕ переробляється — оплата додається зверху. Якщо доводиться щось ламати, значить, план порушено.

---

## Загальні правила під час розробки

- Один етап — одна зв'язна задача. Не змішувати.
- Після кожного етапу — перевірка, що працює, перш ніж далі.
- Складні кроки — просити Claude Code показати план перед виконанням.
- Тестові дані (кілька товарів) додати рано, щоб було на чому перевіряти.
- Не чіпати логіку оплати, поки MVP не готовий.

## Git-дисципліна та звітність

- Репозиторій: https://github.com/Stanislave19/website-for-store
- **Авторство комітів — тільки власника проєкту.** Жодних згадок Claude / AI / co-authored-by / generated with у повідомленнях комітів.
- Коміт після кожного логічного кроку всередині етапу (не раз на етап) — щоб мати точні точки відкату.
- Осмислені повідомлення комітів: що змінилось і навіщо.
- Регулярний пуш на GitHub.
- Перед міграціями, зміною схеми чи рефактором — коміт ДО зміни.
- Після кожного кроку — коротке пояснення простою мовою: що зроблено, що тепер працює.
- **Обов'язково — інструкція перевірки вручну**: точна команда для запуску (щоб скопіювати), адреса в браузері, і що саме має бути видно, якщо все правильно. Плюс типові помилки й що вони означають.
